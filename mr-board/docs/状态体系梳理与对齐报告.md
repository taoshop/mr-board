## 1. 背景与目标

当前看板已完成从旧状态体系（开发中/测试中/可合并/冲突/已合并/已关闭/构建失败）向新 7 列状态体系的迁移。本次梳理旨在：

1. 明确 Git 平台原生状态（PR/MR 状态）与 mr-board 看板状态的映射关系；
2. 识别当前映射中的语义重叠与歧义；
3. 确认 PR #6 二轮评审意见的修复落地情况；
4. 给出后续可选的增强建议。

## 2. 状态定义

### 2.1 Git 平台原生状态（platformStatus）

| 平台 | 原生状态值 | 说明 |
|------|-----------|------|
| GitHub | `open` | PR 打开中 |
| GitHub | `closed` | PR 已关闭（未合并） |
| GitHub | `merged` | PR 已合并 |
| GitHub | `draft` | 草稿 PR（通过 `draft=true` 字段或 title 前缀标识） |
| GitLab | `opened` / `open` | MR 打开中 |
| GitLab | `closed` | MR 已关闭 |
| GitLab | `merged` | MR 已合并 |

### 2.2 mr-board 看板状态（boardStatus）— 7 列

| 状态码 | 中文标签 | 主题色 | 业务含义 |
|--------|---------|--------|---------|
| `pending_review` | 待 Review | `#909399` | 无 reviewer 指派，或 review 尚未开始 |
| `reviewing` | Review 中 | `#e6a23c` | 有 reviewer，但未 approved（或被 request changes） |
| `ci_checking` | CI 检查中 | `#409eff` | CI 正在运行或等待中 |
| `conflict` | 冲突待解决 | `#f56c6c` | **阻塞合并区**：包含代码冲突、CI 失败、approved 但不可合并 |
| `ready` | 可合并 | `#67c23a` | CI 通过 + Review 通过 + 无冲突 + mergeable |
| `merged` | 已合并 | `#409eff` | 已合并（终态） |
| `closed` | 已关闭 | `#909399` | 已关闭（终态） |

### 2.3 辅助状态字段

| 字段 | 类型 | 取值示例 | 用途 |
|------|------|---------|------|
| `ciStatus` | String | `success` / `failed` / `running` / `pending` / `unknown` | 描述 CI 流水线结果 |
| `approvalStatus` | String | `pending` / `reviewing` / `approved` / `changes_requested` | 描述 Review 审批结果 |
| `hasConflict` | Boolean | `true` / `false` | 是否存在代码冲突 |
| `mergeable` | Boolean | `true` / `false` | Git 平台是否允许合并 |
| `reviewers` | String | `"user1,user2"` | 被指派的 reviewer 列表 |

## 3. 状态映射逻辑

### 3.1 当前映射全景图（BoardStatusCalculator）

```
platformStatus
├── merged ──────────────────────────────────────────────→ merged
├── closed ──────────────────────────────────────────────→ closed
└── open
    ├── title.startsWith("draft:") / "wip:" ─────────────→ pending_review
    ├── hasConflict = true ──────────────────────────────→ conflict（代码冲突）
    ├── ciStatus = running / pending ────────────────────→ ci_checking
    ├── ciStatus = failed ───────────────────────────────→ conflict（CI 失败）
    └── 以上均无
        ├── 无 reviewer 或 approvalStatus = pending ─────→ pending_review
        ├── approvalStatus = changes_requested ──────────→ reviewing
        ├── approvalStatus = reviewing ──────────────────→ reviewing
        ├── approvalStatus = approved
        │   ├── mergeable = true ────────────────────────→ ready
        │   └── mergeable = false ───────────────────────→ conflict（非冲突原因）
        └── 其他 ────────────────────────────────────────→ pending_review
```

### 3.2 关键映射规则说明

| 规则 | 优先级 | 说明 |
|------|--------|------|
| 终态优先 | 最高 | `merged` / `closed` 不受其他字段影响，直接映射 |
| Draft/WIP 拦截 | 高 | 标题前缀匹配，避免未完成 MR 进入后续流程 |
| 代码冲突拦截 | 高 | `hasConflict=true` 直接落入 `conflict`，不受 review/ci 影响 |
| CI 状态 | 中 | `running/pending` → `ci_checking`；`failed` → `conflict` |
| Review 状态 | 中 | 决定 `pending_review` / `reviewing` / `ready` |
| 可合并校验 | 低 | `approved` 且 `mergeable=true` 才能进入 `ready` |

## 4. 问题诊断

### 4.1 `conflict` 列语义过载（当前最主要问题）

当前 3 种完全不同的阻塞原因都落入同一红色列，造成用户认知混淆：

| 实际原因 | 进入条件 | 当前视觉表现 | 用户误解风险 |
|---------|---------|-------------|-------------|
| **代码冲突** | `hasConflict=true` | 红色边框 + 红色顶部条 | 正确理解 |
| **CI 失败** | `ciStatus=failed` | 红色边框 + 红色顶部条 | 误以为是代码冲突，实则是构建/测试失败 |
| **approved 但不可合并** | `approval=approved && mergeable=false` | 红色边框 + 红色顶部条 | 误以为是代码冲突，实则是分支保护规则或需变基 |

**影响：** 用户看到 `conflict` 列中的卡片，无法直观判断具体阻塞原因，可能采取错误的修复动作（如去拉代码解决冲突，而实际是 CI 失败）。

### 4.2 `ci_checking` 列内缺乏细分

- `ciStatus=running`（CI 正在执行）和 `ciStatus=pending`（CI 等待排队）都显示为 `ci_checking`；
- 卡片上仅有一个 14px 的 `CiStatusIcon`，在列内无法快速区分"正在跑"和"还没开始"。

### 4.3 Draft 检测精度不足

- 当前仅通过 `title` 前缀 `draft:` / `wip:` 检测；
- GitHub 原生提供 `draft=true` 字段，未充分利用；
- GitLab 提供 `work_in_progress=true` 字段，未充分利用。

## 5. PR #6 二轮评审修复落地情况

| 序号 | 评审意见 | 根因分析 | 修复文件 | 修复方式 | 状态 |
|------|---------|---------|---------|---------|------|
| 1 | GitHub `COMMENTED` review 被归类为 `reviewing` | `fetchApprovalStatus` 中只要有 review 记录就返回 `reviewing`，未区分 COMMENTED 和实质评审 | `GitHubClient.java` | 引入 `hasMeaningfulReview` 标志，纯 `COMMENTED` 返回 `pending_review` | ✅ 已落地 |
| 2 | `@Async` 自调用代理绕过 | `triggerSyncAsync` 内部调用 `triggerSync`，Spring AOP 代理不生效，导致同步仍在主线程执行 | `SyncService.java` | `triggerSyncAsync` 逻辑内联，直接写同步循环，不再调用 `triggerSync` | ✅ 已落地 |
| 3 | 卡片点击/拖拽冲突 | 拖拽卡片时，释放鼠标会触发 `@click`，导致打开详情抽屉 | `MrCard.vue` | 增加 `mousedown` 坐标记录，`click` 时检测位移 > 5px 则阻止事件 | ✅ 已落地 |
| 4 | RecycleScroller 高度不一致 | 卡片内容（标题行数、reviewer、CI）高度可变，`item-size=160` 与实际 DOM 高度不匹配，导致滚动错位 | `DashboardView.vue` | 将 `RecycleScroller` 替换为 `DynamicScroller` + `DynamicScrollerItem`，自适应实际高度 | ✅ 已落地 |
| 5 | approved 但不可合并缺少解释 | `approval=approved && mergeable=false` 的卡片落入 `conflict` 列，用户不知道具体原因 | `MrCard.vue` | 条件渲染 `el-tooltip`："已批准但不可合并：可能是分支保护规则或需要变基" | ✅ 已落地 |
| 6 | CI 在列中区分不清 | `ciFailed` 与 `ciRunning` 都映射到 `ci_checking`，导致列内同时存在"CI 失败"和"CI 运行中"的卡片 | `BoardStatusCalculator.java` | 将 `ciFailed` 从 `ci_checking` 分离，映射到 `conflict`（阻塞合并） | ✅ 已落地 |

## 6. 对齐方案建议

### 6.1 方案 A：增强列内语义标签（最小改动，推荐）

**核心思路：** 保持 7 列状态体系不变，在 `conflict` 和 `ci_checking` 列的卡片上增加**次级原因标签**，让用户一眼知道具体阻塞原因。

#### 6.1.1 `conflict` 列卡片增强

在 `MrCard.vue` 的 `card-header` 区域增加一个小型标签：

| 实际原因 | 判断条件 | 标签文案 | 标签颜色 |
|---------|---------|---------|---------|
| 代码冲突 | `hasConflict=true` | `代码冲突` | `danger` |
| CI 失败 | `ciStatus=failed` | `CI 失败` | `danger` |
| 不可合并 | `approval=approved && mergeable=false` | `需变基/保护规则` | `warning` |

**预期效果：** 用户看到 `conflict` 列时，能通过标签快速区分"需要解冲突"、"需要修 CI"、"需要变基"。

#### 6.1.2 `ci_checking` 列卡片增强

在 `MrCard.vue` 的 `ci` 区域增加文字说明：

| ciStatus | 图标表现 | 文案 |
|---------|---------|------|
| `running` | 橙色旋转 Loading | `CI 运行中` |
| `pending` | 灰色 Minus | `CI 等待中` |

#### 6.1.3 后端影响

无需修改。`BoardStatusCalculator` 的映射逻辑保持不变，因为：
- `conflict` 列作为"阻塞合并区"是合理的业务抽象；
- 具体阻塞原因已由 `hasConflict`、`ciStatus`、`mergeable` 字段携带；
- 前端仅做展示层增强，不改动状态流转规则。

### 6.2 方案 B：拆分 `conflict` 为两列（较大改动，不建议）

| 新状态码 | 中文标签 | 进入条件 |
|---------|---------|---------|
| `conflict` | 代码冲突 | `hasConflict=true` |
| `ci_failed` | CI 失败 | `ciStatus=failed` |

**缺点：**
- 看板从 7 列 → 8 列，横向空间更紧张；
- 需要修改前后端状态常量、拖拽校验规则、报表统计口径等大量文件；
- `approved 但不可合并` 仍然需要归属到某一列，问题未完全解决。

**结论：** 投入产出比低，不建议在当前阶段实施。

### 6.3 方案 C：状态矩阵重构（远期规划）

将"阻塞原因"从状态值中剥离，看板状态只保留流程阶段：
- `pending_review` / `reviewing` / `ready` / `merged` / `closed`
- CI 状态作为独立维度图标展示
- 冲突/失败作为卡片上的独立标签展示

**缺点：** 改动量极大，涉及前后端所有状态流转逻辑、历史数据兼容、用户习惯迁移。

**结论：** 适合作为 v2.0 重大改版时考虑，当前阶段不适用。

## 9. 结论与下一步行动

1. **当前 7 列状态体系是合理的**，问题不在于状态划分，而在于 `conflict` 列的**语义表达不足**。
2. **PR #6 二轮评审的 6 项意见已全部修复并编译通过**，可直接提交代码。
3. **推荐采用方案 A**（增强列内语义标签）作为后续优化：
   - 仅修改 `MrCard.vue`，改动量极小；
   - 不改动状态体系和数据模型，无兼容性风险；
   - 能显著降低用户对 `conflict` 列的认知成本。
