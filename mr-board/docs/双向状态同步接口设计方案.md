# 双向状态同步接口设计方案

**编制日期：** 2026-07-26  
**关联报告：** `GitHub-GitLab-MR生命周期与状态流转报告.md`  
**目标：** 将 mr-board 从「平台 → 本地单向同步」升级为「平台 ↔ 本地双向同步」

---

## 1. 现状分析

| 冲突检测 | **本地修改 vs 平台更新** | ❌ 无 | ❌ 未实现 | — |

### 1.2 核心问题

1. **评论单向：** 用户在 mr-board 看板上只能「看」评论，不能「发」评论；本地评论与平台评论割裂。
2. **Reviewer 管理缺失：** 无法在看板上指派或移除 reviewer，必须跳转到 GitHub/GitLab 操作。
3. **Draft/WIP 状态无法切换：** 看板上无法将 PR 标记为 Draft 或 Ready for review。
4. **CI 重跑入口缺失：** 发现 CI 失败后，无法在看板上直接触发重跑。
5. **同步冲突无感知：** 用户在 mr-board 上修改了状态/评论，同时平台侧也有更新，下次同步会直接覆盖本地修改，无冲突提示。

### 2.2 平台 API 映射详表

#### 2.2.1 添加评论

| 平台 | API Endpoint | Method | Body | 认证头 |
|------|-------------|--------|------|--------|
| **GitHub** | `/repos/{owner}/{repo}/issues/{number}/comments` | POST | `{"body": "..."}` | `Authorization: token {token}` |
| **GitLab** | `/projects/{encodedPath}/merge_requests/{iid}/notes` | POST | `{"body": "..."}` | `PRIVATE-TOKEN: {token}` |

> **注意：** GitHub PR 的评论实际上走 Issues API（PR 也是 issue），返回字段为 `id`, `body`, `user.login`, `created_at`。

#### 2.2.2 指派/移除 Reviewer

| 平台 | 操作 | API Endpoint | Method | Body |
|------|------|-------------|--------|------|
| **GitHub** | 添加 | `/repos/{owner}/{repo}/pulls/{number}/requested_reviewers` | POST | `{"reviewers": ["alice"]}` |
| **GitHub** | 移除 | `/repos/{owner}/{repo}/pulls/{number}/requested_reviewers` | DELETE | `{"reviewers": ["alice"]}` |
| **GitLab** | 添加 | `/projects/{encodedPath}/merge_requests/{iid}` | PUT | `{"reviewer_ids": [userId1, userId2]}` |
| **GitLab** | 移除 | `/projects/{encodedPath}/merge_requests/{iid}` | PUT | `{"reviewer_ids": [剩余用户ID数组]}` |

> **GitLab 难点：** GitLab API 要求传 `reviewer_ids`（数字 ID 数组），而不是 username。需要先调用 `/users?username={name}` 获取 userId，或者缓存 username → userId 映射。
> **建议方案：** 在 `GitLabClient` 内部维护 username → userId 的本地缓存，失效时间 1 小时。

#### 2.2.3 更新标题（Draft/WIP 切换）

| 平台 | API Endpoint | Method | Body |
|------|-------------|--------|------|
| **GitHub** | `/repos/{owner}/{repo}/pulls/{number}` | PATCH | `{"title": "Draft: xxx"}` |
| **GitLab** | `/projects/{encodedPath}/merge_requests/{iid}` | PUT | `{"title": "WIP: xxx"}` |

> **Draft/WIP 语义差异处理：**
> - GitHub：Patch title 加 `Draft:` 前缀即自动变为 draft；但 API 也支持直接 PATCH `{"draft": true/false}`（更精确）
> - GitLab：Patch title 加 `WIP:` 前缀即自动变为 WIP；新版 GitLab 也支持 `{"draft": true}`
> - **推荐实现：** GitHub 使用 `draft` 字段 PATCH；GitLab 使用 title 前缀（兼容旧版）+ 检测 `draft` 字段（新版）

#### 2.2.4 重跑 CI

| 平台 | API Endpoint | Method | Body | 说明 |
|------|-------------|--------|------|------|
| **GitHub** | `/repos/{owner}/{repo}/actions/runs/{runId}/rerun-failed-jobs` | POST | — | 需要获取失败的 check-run 对应的 workflow run id |
| **GitHub（替代）** | `/repos/{owner}/{repo}/actions/runs/{runId}/rerun` | POST | — | 重跑整个 workflow |
| **GitLab** | `/projects/{encodedPath}/pipelines/{pipelineId}/retry` | POST | — | retry 整个 pipeline |

> **GitHub 难点：** Check Run 与 Workflow Run 是不同概念。Check Run 没有直接的 "rerun" API，需要找到对应的 Workflow Run ID。> **建议方案：** GitHub 侧 `rerunCi()` 实现为：> 1. 获取 PR head commit 的所有 check runs
> 2. 找到对应的 check suite → 提取 `check_suite.id`
> 3. 通过 GraphQL 或 Actions API 找到 workflow run id（GitHub 暂未提供 REST API 直接映射 check suite → workflow run）
> 4. 如果无法精确映射，可降级为：返回 MR webUrl，让前端跳转去平台手动重跑
> 
> **GitLab 侧相对简单：** 直接调用 pipeline retry API。

## 3. 同步冲突检测机制

### 3.1 问题定义

当用户在 mr-board 上做了本地修改（如拖拽状态、添加评论、指派 reviewer），但尚未同步到平台；此时平台侧也有了更新（如有人新 push 了代码、CI 状态变化、其他人合并了 MR）。下次 `SyncService` 定时同步时，会直接覆盖本地修改，导致用户操作丢失。

### 3.2 冲突检测策略：基于时间戳的三态模型

利用 `Mrs` 表中已有的两个时间戳字段：

| 字段 | 含义 | 现有状态 |
|------|------|---------|
| `lastSyncAt` | 上次从平台成功同步的时间 | ✅ 已存在 |
| `localUpdatedAt` | 本地记录最后一次被修改的时间（含手动拖拽、评论等） | ✅ 已存在（@TableField(fill=INSERT_UPDATE)）|

#### 三态判定逻辑

```
平台数据更新时间（platformUpdatedAt） vs 本地时间戳

IF platformUpdatedAt <= lastSyncAt:
    → 平台无新数据，安全写入
ELSE IF platformUpdatedAt > lastSyncAt AND localUpdatedAt <= lastSyncAt:
    → 平台有更新，本地无修改，安全覆盖
ELSE IF platformUpdatedAt > lastSyncAt AND localUpdatedAt > lastSyncAt:
    → 冲突！平台更新了，本地也修改了
```

#### 冲突处理策略

| 冲突字段 | 平台优先 | 本地优先 | 合并策略 | 建议 |
|---------|---------|---------|---------|------|
| `boardStatus`（拖拽看板） | 下次同步覆盖 | 保留本地 | 无 | **本地优先** + 提示用户 |
| `reviewers`（指派 reviewer） | 平台为准 | 本地为准 | 并集 | **并集策略** |
| `comments`（评论） | 追加平台 | 追加本地 | 时间序合并 | **时间序合并** |
| `title`（Draft 切换） | 平台为准 | 本地为准 | 以时间 newer 为准 | **时间 newer 优先** |
| `platformStatus`（合并/关闭） | 终态优先 | 终态优先 | 终态优先 | **终态永远优先** |

### 3.3 具体实现方案

#### 3.3.1 字段级冲突检测（推荐）

在 `SyncService.saveOrUpdateMr()` 中增加冲突检测：

```java
private Mrs saveOrUpdateMr(Long projectId, MrDTO dto, GitSyncClient client) {
    // ... 现有查询逻辑 ...
    
    if (existing != null) {
        // 获取平台侧更新时间（GitHub: updated_at, GitLab: updated_at）
        LocalDateTime platformUpdatedAt = dto.getUpdatedAt();
        
        // 冲突检测
        if (platformUpdatedAt != null 
                && platformUpdatedAt.isAfter(existing.getLastSyncAt())
                && existing.getLocalUpdatedAt() != null
                && existing.getLocalUpdatedAt().isAfter(existing.getLastSyncAt())) {
            
            // 发生冲突，按字段级策略处理
            log.warn("Sync conflict detected for MR {} in project {}", dto.getPlatformMrId(), projectId);
            
            // platformStatus 终态优先
            if (isTerminalStatus(dto.getPlatformStatus())) {
                existing.setPlatformStatus(dto.getPlatformStatus());
                existing.setBoardStatus(mapTerminalStatus(dto.getPlatformStatus()));
            }
            
            // CI 状态：平台优先（CI 是客观事实）
            existing.setCiStatus(dto.getCiStatus());
            
            // title：以时间 newer 为准
            if (platformUpdatedAt.isAfter(existing.getLocalUpdatedAt())) {
                existing.setTitle(dto.getTitle());
            }
            
            // reviewers：并集策略
            mergeReviewers(existing, dto.getReviewers());
            
            existing.setConflictFlag(true); // 标记冲突，供前端提示
        } else {
            // 无冲突，正常覆盖
            // ... 现有赋值逻辑 ...
        }
        
        mrsMapper.updateById(existing);
        return existing;
    }
    
    // ... 新建逻辑 ...
}
```

#### 3.3.2 数据库变更

新增 `conflict_flag` 字段用于标记同步冲突：

```sql
ALTER TABLE mrs ADD COLUMN conflict_flag TINYINT(1) DEFAULT 0 COMMENT '同步冲突标记：1=上次同步检测到冲突';
```

前端看板可对 `conflict_flag=1` 的卡片增加视觉提示（如右上角小圆点或边框闪烁）。

### 3.4 评论的双向合并策略

评论是「追加型」数据，天然适合合并：

```
平台评论列表 (platformComments)
本地评论列表 (localComments，指 mr-board 用户创建但尚未同步到平台的评论)

合并结果 = platformComments ∪ localComments

去重键 = platformCommentId（本地创建但未同步的评论先用临时 UUID，同步成功后更新为平台 ID）
```

**实现要点：**
- `mr_comments` 表增加 `sync_status` 字段：`pending` / `synced` / `failed`
- 用户在看板上发表评论 → `sync_status=pending`，同时尝试调用 `GitSyncClient.addComment()`
- 如果 API 调用成功 → `sync_status=synced`，更新 `platformCommentId`
- 如果 API 调用失败 → `sync_status=failed`，保留本地数据，前端显示 "发送失败，点击重试"
- 同步时，平台拉取的评论与本地 `synced` 评论按 `createdAt` 排序展示

## 5. 时序与边界场景

### 5.1 评论发送时序

```
用户在看板输入评论点击发送
        │
        ▼
   ┌────────────────────────────────────┐
   │ 1. 前端乐观展示（本地时间戳）         │
   │    UI 立即显示评论，状态为「发送中」   │
   └────────────────────────────────────┘
        │
        ▼
   ┌────────────────────────────────────┐
   │ 2. 调用 POST /api/mrs/{id}/comments │
   │    后端调用 GitSyncClient.addComment │
   └────────────────────────────────────┘
        │
        ├─── 平台 API 成功 ───→ 本地标记 synced，前端显示「已发送」
        │
        └─── 平台 API 失败 ───→ 本地标记 failed，前端显示「发送失败，点击重试」
                    │
                    ▼
            用户点击重试，回到步骤 2
```

### 5.2 Draft 切换时序

```
用户点击「标记为 Draft」
        │
        ▼
   ┌────────────────────────────────────┐
   │ 1. 调用 PUT /api/mrs/{id}/draft?draft=true │
   │    后端调用 GitSyncClient.updateMrTitle    │
   └────────────────────────────────────┘
        │
        ├─── 成功 ───→ 本地 title 更新，boardStatus 重新计算为 pending_review
        │
        └─── 失败 ───→ 提示错误，本地状态不变
```

### 5.3 同步冲突边界场景

| 场景 | 用户操作 | 平台变化 | 预期行为 |
|------|---------|---------|---------|
| **场景 A** | 用户将 MR 从 `ready` 拖到 `conflict`（手动标记有问题） | 平台无变化 | 下次同步：平台 updatedAt <= lastSyncAt，安全保留本地状态 |
| **场景 B** | 用户在看板上发表了一条评论 | 同时有新 push，CI 状态变化 | 下次同步：检测到冲突（platformUpdatedAt > lastSyncAt 且 localUpdatedAt > lastSyncAt）。评论保留（追加），CI 状态更新为平台值，boardStatus 按规则重新计算 |
| **场景 C** | 用户在看板上指派了 reviewer | 平台侧有人合并了 MR | 下次同步：platformStatus=merged（终态），终态优先 → 本地 boardStatus 强制变为 `merged`，reviewer 指派操作被静默丢弃（合理，因为 MR 已合并） |
| **场景 D** | 用户在看板上将 MR 标记为 Draft | 平台侧有人关闭了 MR | 下次同步：platformStatus=closed（终态优先），本地 Draft 标记被覆盖，boardStatus → `closed` |

## 7. 关键实现细节

### 7.1 GitHub Check Suite → Workflow Run 映射（rerunCi 降级方案）

GitHub REST API 暂未提供从 Check Run/Check Suite 直接获取 Workflow Run ID 的公开接口。建议实现：

```java
@Override
public boolean rerunCi(String projectPath, Long mrIid) {
    // 方案 A（推荐）：获取 PR head commit → 列出 check suites →
    // 通过 check_suite.app.id 过滤 GitHub Actions →
    // 调用 GraphQL 查询 workflow run（如果配置了 GraphQL token）
    
    // 方案 B（降级）：直接返回 false，让前端引导用户到平台重跑
    log.warn("GitHub rerunCi not fully supported via REST API, please rerun manually at webUrl");
    return false;
}
```

前端降级表现：点击「重跑 CI」时，如果后端返回 `501 Not Implemented` 或特定错误码，弹窗提示 "GitHub 暂不支持在看板内重跑 CI，请跳转到 PR 页面操作"，并提供 `webUrl` 链接。

### 7.2 GitLab userId 缓存

```java
@Component
public class GitLabUserIdCache {
    private final Map<String, Long> cache = new ConcurrentHashMap<>(); // key = apiBaseUrl + ":" + username
```

### 7.3 评论去重键

GitHub 评论 API 返回的 `id` 是全局唯一的数字 ID；GitLab note API 返回的 `id` 也是全局唯一。本地表 `mr_comments.platform_comment_id` 已存在，可直接用作去重键。

对于「本地创建但未同步」的评论，使用临时前缀 `local-{uuid}` 作为 `platform_comment_id`，同步成功后更新为平台返回的真实 ID。

## 8. 结论

双向状态同步的核心是**「读优先覆盖客观事实，写保留用户意图」**：

- **客观事实**（CI 状态、platformStatus、代码冲突、合并时间）以平台数据为准；
- **用户意图**（评论、reviewer 指派、Draft 标记、看板手动拖拽）需要回写平台，并在冲突时做合理合并；
- **终态**（merged/closed）永远是最高优先级，一旦平台进入终态，本地所有未同步的修改都应被覆盖。

建议按 **P0 → P1 → P2** 分阶段实施，先落地评论和冲突检测，再逐步补全 reviewer 管理和 Draft 切换。
