## 2. 项目概述

### 2.1 背景
在软件开发团队中，Merge Request（MR）是代码合并前的核心质量关卡。随着项目规模扩大，MR 数量激增，PM 与 Tech Lead 缺乏统一的视图来跟踪所有进行中的 MR 状态，导致：
- 代码评审进度不透明，瓶颈 MR 无法及时发现
- CI 失败或合并冲突的 MR 未能及时处理，阻塞发布节奏
- 缺乏数据支撑，无法量化团队研发效能

### 2.2 目标
构建一个**Git 分支合并请求状态看板系统**，通过对接 GitLab/GitHub API，实现 MR 数据的自动同步、可视化看板跟踪、多维筛选、状态流转、统计报表与权限管控，提升团队协作效率与研发透明度。

### 2.3 业务范围
- 支持 GitLab / GitHub 双平台 MR 数据同步
- 覆盖 MR 全生命周期：创建 → Review → CI → 冲突解决 → 合并/关闭
- 提供看板、列表、详情、报表四种核心视图
- 支持基于角色的权限控制与数据范围隔离

## 4. 功能需求

### 4.1 MR 数据同步模块

#### 4.1.1 Git 平台对接配置
- 支持配置多个 Git 源（GitLab / GitHub），每个源包含：
  - 平台类型（GitLab / GitHub）
  - API 基础地址（如 `https://gitlab.company.com/api/v4`）
  - 访问令牌（Personal Access Token / OAuth Token）
  - 监听的项目列表（Project Path / Repository Full Name）
  - 同步周期（CRON 表达式，如每 5 分钟）
- 支持手动触发全量同步与增量同步
- 同步任务日志记录（成功/失败/耗时）

#### 4.1.2 同步数据字段
| 字段 | 来源 | 说明 |
|---|---|---|
| MR 编号（iid） | Git API | 项目内唯一编号 |
| 标题 | Git API | MR 标题 |
| 描述 | Git API | MR 描述内容 |
| 提交人（Author） | Git API | 创建者用户名、邮箱、头像 |
| 指派人（Assignee） | Git API | 负责处理者 |
| Reviewer 列表 | Git API | 被指定评审人 |
| 源分支 | Git API | source_branch |
| 目标分支 | Git API | target_branch |
| 创建时间 | Git API | created_at |
| 更新时间 | Git API | updated_at |
| 合并时间 | Git API | merged_at（如已合并） |
| 关闭时间 | Git API | closed_at（如已关闭） |
| 平台状态 | Git API | opened / merged / closed |
| 合并冲突标志 | Git API | has_conflicts / mergeable |
| CI 流水线状态 | Git API | pipeline/status checks |
| 变更文件数 | Git API | changes_count |
| 添加/删除行数 | Git API | additions / deletions |
| 评论数 | Git API | user_notes_count |
| Web URL | Git API | 直达 Git 平台 MR 页面链接 |

#### 4.1.3 同步策略
- **增量同步**：基于 `updated_at` 或 Webhook 事件，仅同步变更数据
- **全量同步**：首次接入或手动触发时，拉取所有历史 MR
- **冲突处理**：以 Git 平台数据为准，本地状态字段保留用户在看板上的操作标记

### 4.2 状态看板模块

#### 4.2.1 看板列定义（系统状态）
系统基于 Git 平台状态与 CI/冲突状态，将 MR 映射到以下看板列：

| 看板列 | 进入条件 | 颜色标识 |
|---|---|---|
| **待 Review** | 平台状态=opened，无进行中的 CI，无冲突，未开始 Review | 灰色 |
| **Review 中** | 平台状态=opened，已有 Reviewer 且存在评审活动（评论/Approval），无冲突 | 蓝色 |
| **CI 检查中** | 平台状态=opened，CI 状态=running / pending | 橙色 |
| **冲突待解决** | 平台状态=opened，mergeable=false 或 has_conflicts=true | 🔴 红色高亮 |
| **可合并** | 平台状态=opened，CI 通过，无冲突，Review 通过（如需） | 绿色 |
| **已合并** | 平台状态=merged | 紫色 |
| **已关闭** | 平台状态=closed | 深灰 |

#### 4.2.2 看板卡片展示
每张卡片至少展示：
- MR 编号 + 标题（截断显示，hover 显示完整标题）
- 提交人头像 + 名称
- 源分支 → 目标分支（分支名过长时截断）
- CI 状态图标（✅成功 / ❌失败 / ⏳进行中 / ⚪无）
- 冲突警告图标（如存在冲突）
- 评论数徽章
- 变更文件数 / 代码行变更数
- 创建时间（相对时间，如"2小时前"）
- 标签（Labels，彩色小徽章）

#### 4.2.3 拖拽变更状态
- 用户可在看板列之间拖拽卡片，变更 MR 的系统状态
- **双向同步策略**：
  - 若拖拽后的状态仅涉及系统内部看板列（如"待 Review"→"Review 中"），仅更新本地状态
  - 若拖拽到"已合并"列，系统尝试调用 Git API 执行 Merge 操作（需确认权限与冲突状态）
  - 若拖拽到"已关闭"列，系统尝试调用 Git API 关闭 MR
  - 若从"冲突待解决"拖出，系统提示用户先解决冲突
- 拖拽操作记录操作日志（操作人、时间、原状态、新状态）
- 无权限用户无法拖拽（卡片置灰或禁止拖动）

---

### 4.3 CI 状态集成模块

#### 4.3.1 CI 数据同步
- 同步 MR 关联的 CI Pipeline / Status Checks 信息：
  - CI 提供商（GitLab CI / GitHub Actions / Jenkins / 其他）
  - 流水线 ID、名称、触发分支
  - 各 Stage / Job 状态
  - 日志链接

#### 4.3.2 CI 状态标识规则
| 状态 | 图标 | 说明 |
|---|---|---|
| 成功（success） | 绿色勾选 | 所有检查通过 |
| 失败（failed） | 红色叉号 | 至少一个 Job 失败 |
| 进行中（running/pending） | 橙色转圈 | 有 Job 正在执行 |
| 已取消（canceled） | 灰色禁止 | 手动取消 |
| 无 CI | — | 未配置 CI |

- 卡片上以图标形式展示整体 CI 状态
- 详情面板展示各 Stage/Job 的详细状态与日志链接

---

### 4.4 冲突标识模块

#### 4.4.1 冲突检测
- 每次同步时检查 `mergeable` / `has_conflicts` 字段
- 若检测到冲突，卡片在看板中**标红高亮**，并在卡片顶部显示红色冲突条带
- 冲突 MR 禁止直接拖拽到"可合并"或"已合并"列

#### 4.4.2 冲突提示
- 卡片 hover 时显示提示："存在合并冲突，请先在本地解决后推送"
- 详情页展示冲突文件列表（如 API 支持）

---

### 4.5 多维筛选模块

#### 4.5.1 筛选维度
| 维度 | 类型 | 说明 |
|---|---|---|
| 提交人 | 多选下拉 | 按 MR 作者筛选 |
| Reviewer | 多选下拉 | 按指定评审人筛选 |
| 项目 | 多选下拉 | 按 Git 项目/仓库筛选 |
| 目标分支 | 多选下拉 | 如 main、develop、release/* |
| 状态 | 多选 | 看板列状态 |
| CI 状态 | 多选 | 成功/失败/进行中/无 |
| 冲突状态 | 单选 | 全部/有冲突/无冲突 |
| 时间范围 | 日期范围 | 创建时间/更新时间 |
| 关键词 | 文本输入 | 匹配标题、描述、MR 编号 |
| 标签 | 多选 | Git 平台 Label 筛选 |

#### 4.5.2 筛选交互
- 筛选条件支持组合（AND 关系）
- 支持保存常用筛选为"快捷视图"（个人级）
- 支持筛选条件重置
- 筛选结果实时更新看板与统计数字

---

### 4.6 MR 详情模块

#### 4.6.1 详情面板内容
- **基本信息**：编号、标题、描述、提交人、创建时间、各状态时间线
- **分支信息**：源分支、目标分支、与目标分支的落后/领先提交数
- **变更文件**：文件列表（文件名、状态：新增/修改/删除、变更行数），支持点击展开 diff（或跳转 Git 平台）
- **评论**：展示 MR 下的评论线程，支持查看已解决/未解决状态
- **CI 详情**：各 Stage/Job 状态矩阵，点击跳转日志链接
- **活动日志**：MR 在本系统的状态变更记录（谁在什么时间将 MR 从 X 状态改为 Y 状态）

#### 4.6.2 交互
- 点击看板卡片打开侧边栏详情（右侧滑出，不离开当前看板）
- 提供"在 Git 平台打开"按钮，跳转原始 MR 页面

---

### 4.7 统计报表模块

#### 4.7.1 统计维度
- **时间维度**：按周 / 按月统计
- **项目维度**：按项目/仓库聚合
- **人员维度**：按提交人 / Reviewer 聚合

#### 4.7.2 核心指标
| 指标 | 计算方式 |
|---|---|
| MR 提交数量 | 周期内创建的 MR 数 |
| MR 合并数量 | 周期内合并的 MR 数 |
| MR 关闭数量 | 周期内关闭（未合并）的 MR 数 |
| 平均合并时长 | 所有已合并 MR 的（merged_at - created_at）平均值 |
| 中位合并时长 | 同上，取中位数 |
| 各状态分布 | 统计周期结束时各看板列的 MR 数量 |
| CI 成功率 | CI 成功的 MR 数 / 有 CI 的 MR 总数 |
| 冲突率 | 曾出现冲突的 MR 数 / MR 总数 |
| Review 平均轮次 | MR 从待 Review 到可合并的平均状态变更次数 |

#### 4.7.3 展示形式
- **概览卡片**：顶部展示关键指标（本周 MR 数、平均合并时长、CI 成功率、冲突率）
- **趋势图**：折线图展示 MR 提交/合并趋势（按日/周）
- **分布图**：
  - 柱状图：各状态 MR 数量分布
  - 饼图/环形图：各项目 MR 占比
  - 堆叠柱状图：各人员 MR 状态分布
- **表格明细**：支持按维度下钻，展示具体 MR 列表

#### 4.7.4 导出功能
- 支持将报表数据导出为 **Excel (.xlsx)** 与 **CSV (.csv)**
- 导出内容包含当前筛选条件下的完整数据（含所有字段）
- 导出报表模板支持按周/月自动生成并下载

### 4.8 用户登录与权限模块

#### 4.8.1 认证方式
- 支持**本地账号密码登录**（系统内置）
- 支持**OAuth 2.0 登录**（对接企业 GitLab / GitHub SSO，可选）
- JWT Token 机制，支持 Token 刷新与过期处理

#### 4.8.2 角色与权限模型（RBAC）
- **用户（User）**：基础实体，含用户名、邮箱、头像、所属部门/团队
- **角色（Role）**：Developer、Reviewer、Tech Lead、PM、Admin
- **权限（Permission）**：
  - 菜单级权限：控制可见导航菜单
  - 数据级权限：控制可查看的 MR 数据范围（本人/本团队/本项目/全局）
  - 操作级权限：控制具体按钮/操作（如拖拽、合并、导出）
- **用户-角色**多对多关联
- **角色-权限**多对多关联

#### 4.8.3 菜单权限控制
| 角色 | 可见菜单 |
|---|---|
| Developer | 看板、我的 MR、设置（个人） |
| Reviewer | 看板、待我评审、设置（个人） |
| Tech Lead | 看板、统计报表、团队管理、设置 |
| PM | 看板、统计报表、导出中心、设置 |
| Admin | 全部菜单 + 系统管理（用户、角色、Git 源配置、同步日志） |

## 5. 业务流程

```

  │
  ▼

  ▼

  │
  ▼
[调用 Git API] ──→ 获取 MR 列表与详情
  │
  ▼
[数据解析与映射] ──→ 转换为本系统数据模型
  │
  ▼
[冲突检测] ──→ 标记 mergeable / has_conflicts
  │
  ▼
[CI 状态同步] ──→ 获取关联 Pipeline / Status Checks
  │
  ▼

  │
  ▼

  │
  ▼
[记录同步日志]
  │
  ▼
结束
```

```

  ▼

  ├──→ [拖拽卡片] ──→ 变更状态（有权限时）
```

## 6. 用户场景（Use Cases）

### 场景 1：Developer 跟踪自己的 MR 状态
> **角色**：Developer  
> **背景**：小张刚提交了一个 MR，想查看评审进度和 CI 是否通过。  
> **流程**：
> 1. 小张登录系统，默认进入"我的 MR"看板
> 2. 看到自己的 MR 卡片在"CI 检查中"列，CI 图标为橙色转圈
> 3. 几分钟后刷新，CI 通过，卡片自动移动到"待 Review"列
> 4. 卡片上显示 Reviewer 为李工，小张 hover 卡片查看评论数为 0
> 5. 次日，卡片移动到"Review 中"，评论数变为 3，小张点击卡片查看具体评审意见

### 场景 2：Reviewer 进行 Code Review
> **角色**：Reviewer  
> **背景**：李工被指定为多个 MR 的 Reviewer，需要统一处理。  
> **流程**：
> 1. 李工登录系统，进入"待我评审"看板
> 2. 筛选器已自动选中 Assignee = 李工，状态 = 待 Review / Review 中
> 3. 李工按项目优先级排序，先查看核心项目的 MR
> 4. 点击卡片查看详情，阅读变更文件列表，确认无重大问题
> 5. 李工在 Git 平台完成 Approval，系统下次同步后卡片自动移动到"可合并"

### 场景 3：Tech Lead 识别阻塞风险
> **角色**：Tech Lead  
> **背景**：周五下午，Tech Lead 王工需要确认本周是否能按计划合并所有特性分支。  
> **流程**：
> 1. 王工登录系统，进入全局看板
> 2. 王工注意到"冲突待解决"列有 3 张红色高亮卡片，且已停留超过 2 天
> 3. 王工点击卡片查看提交人，发现均为同一 Developer
> 4. 王工私信该 Developer 提醒优先解决冲突
> 5. 王工切换到统计报表，查看本周平均合并时长为 1.8 天，较上周缩短

### 场景 4：PM 汇报研发效能
> **角色**：PM  
> **背景**：月底 PM 需要向管理层汇报研发团队效能。  
> **流程**：
> 1. PM 登录系统，进入统计报表页面
> 2. 选择时间维度"本月"，聚合维度"按项目"
> 3. 系统展示各项目的 MR 提交数、合并数、平均合并时长、CI 成功率
> 4. PM 发现 A 项目冲突率高达 25%，CI 成功率仅 70%，识别为风险项目
> 5. PM 点击导出按钮，生成 Excel 报表，用于汇报材料

### 场景 5：系统管理员接入新项目
> **角色**：系统管理员  
> **背景**：公司新启动 B 项目，需要接入看板系统。  
> **流程**：
> 1. 管理员进入系统管理 → Git 源配置
> 2. 点击"新增 Git 源"，选择平台类型为 GitLab
> 3. 填写 B 项目的 API 地址、Access Token、监听项目路径
> 4. 点击"测试连接"，系统验证 Token 权限与项目可达性
> 5. 保存配置，触发首次全量同步
> 6. 管理员在用户管理中将 B 项目成员批量导入并分配角色

## 7. 非功能需求

### 7.1 性能需求
- 看板页面首屏加载 ≤ 2 秒（1000 条 MR 以内）
- 筛选操作响应 ≤ 500ms
- 单次 Git API 同步任务 ≤ 30 秒（单项目 500 个 MR 以内）
- 统计报表聚合查询 ≤ 3 秒

### 7.2 可靠性需求
- Git API 同步失败时记录错误日志，支持自动重试（最多 3 次）
- 系统状态与 Git 平台状态不一致时，以 Git 平台为准，下次同步自动修复
- 支持 Webhook 作为增量同步的补充机制，降低 API 调用频率

### 7.3 安全性需求
- Git API Token 加密存储（AES-256 或环境变量注入）
- 所有 API 接口需 JWT 鉴权
- 敏感操作（合并 MR、关闭 MR）需二次确认
- 支持 HTTPS 通信
- 用户密码采用 bcrypt 加密存储

### 7.4 兼容性需求
- 前端适配 Chrome、Firefox、Edge、Safari 最新两个主版本
- 后端 API 遵循 RESTful 规范，返回统一 JSON 格式
- 数据库支持 MySQL 8.0+ / PostgreSQL 13+ / SQLite 3（开发环境）

## 9. 数据模型（核心实体）

### 9.1 实体关系
- **User**（用户）1:N **MR**（作为 Author）
- **User**（用户）N:M **MR**（作为 Reviewer）
- **Project**（项目）1:N **MR**
- **GitSource**（Git 源）1:N **Project**
- **MR** 1:N **CIJob**（CI 任务）
- **MR** 1:N **MRStatusHistory**（状态变更历史）
- **User** N:M **Role**
- **Role** N:M **Permission**

### 9.2 核心表结构提示
- `mrs`：存储 MR 主数据（编号、标题、分支、状态、冲突标志、CI 状态等）
- `mr_reviewers`：MR 与 Reviewer 关联表
- `ci_jobs`：CI 任务详情（名称、状态、日志链接）
- `mr_status_history`：本系统内的状态变更记录
- `git_sources`：Git 平台配置
- `projects`：项目/仓库信息
- `users`、`roles`、`permissions`、`role_permissions`、`user_roles`：RBAC 模型
- `sync_logs`：同步任务日志
