## 二、逐项核验详情

### 1. MR 数据同步 — ✅ 完全满足

**需求：** 通过 GitLab/GitHub API 定时同步 MR 数据（编号/标题/提交人/源分支/目标分支/状态）。

**实现情况：**
- `SyncService` 通过 Quartz 调度器执行 `0 */5 * * * ?` 定时同步（每 5 分钟）。
- `GitHubClient` / `GitLabClient` 支持双平台 API 调用：`fetchMRs`、`fetchReviewers`、`fetchApprovalStatus`、`fetchCI`、`fetchComments`、`fetchChanges`。
- 同步字段完整覆盖：
  - `platformMrId`（编号）、`title`（标题）、`authorName`（提交人）
  - `sourceBranch`（源分支）、`targetBranch`（目标分支）
  - `platformStatus`（平台状态）、`boardStatus`（看板状态，计算产出）
  - `hasConflict`、`mergeable`、`ciStatus`、`reviewers`、`approvalStatus`

**关键文件：**
- `SyncService.java:197-288`（同步流程）
- `GitHubClient.java` / `GitLabClient.java`（平台客户端）

### 6. 拖拽变更 — ✅ 完全满足

**需求：** 支持在看板中拖拽变更 MR 状态（与 Git 平台双向同步）。

**实现情况：**
- 前端拖拽：HTML5 Drag & Drop，`handleDragStart` / `handleDragOver` / `handleDrop`。
- 拖拽规则校验：`canDrop` 禁止冲突 MR 拖入 `ready`/`merged`；终态列不可拖拽；`REVIEWER` 无拖拽权限。
- 权限控制：`DEVELOPER` 只能拖拽自己的 MR；`ADMIN`/`TECHLEAD`/`PM` 可拖拽全部。
- **双向同步：**
  - 拖入 `merged` → 调用 `GitSyncClient.mergeMR` 在平台执行合并。
  - 拖入 `closed` → 调用 `GitSyncClient.closeMR` 在平台关闭。
  - 重新打开 → `MrsController.reopen` 调用 `reopenMR` 在平台重新打开。
- 手动状态覆盖：`manual_status` 字段记录拖拽结果，同步时保留（终态除外）。
- 乐观更新 + 失败回滚：前端先更新视图，失败则回滚并提示。
- 二次确认：拖入 `merged`/`closed` 时弹出 `ElMessageBox.confirm` 提示「此操作将同步到 Git 平台」。
- 状态变更历史：每次拖拽写入 `mr_status_history` 表，记录操作人、IP、时间。

**关键文件：**
- `DashboardView.vue:524-611`（拖拽逻辑）
- `MrsController.java:171-226`（状态更新接口）
- `MrsController.java:356-383`（重新打开接口）

### 9. 用户登录与权限 — ✅ 基本满足

**需求：** 基于角色的访问控制，支持 开发（查看/操作）、Reviewer（评审）、PM/Tech Lead（查看）等角色登录，不同角色看到不同菜单与数据范围。

**实现情况：**
- **认证方式：** JWT + Spring Security（`JwtAuthenticationFilter` + `SecurityConfig`）。
- **角色体系：** `ADMIN`、`PM`、`TECHLEAD`、`DEVELOPER`、`REVIEWER`（`Role.java`、`UserController` 分配）。
- **接口权限：** `@PreAuthorize` 控制，所有业务接口要求 `hasAnyRole('ADMIN','PM','TECHLEAD','DEVELOPER','REVIEWER')`。
- **数据范围：** `BoardController.applyDataScope` 实现行级隔离：
  - `ADMIN`/`PM`/`TECHLEAD`：查看全部 MR。
  - `DEVELOPER`/`REVIEWER`：仅查看自己提交的 MR（`authorName` 匹配）。
- **菜单权限：** `LayoutView.vue` 动态菜单：
  - 所有用户：看板、Git 源配置、同步日志。
  - `admin`/`pm`/`techlead`：统计报表。
  - `admin`：用户管理。
- **操作权限：** `DashboardView.vue` 按角色控制：
  - `REVIEWER`：不可拖拽，无快捷操作按钮。
  - `DEVELOPER`：仅可拖拽/操作自己的 MR。
  - `ADMIN`/`TECHLEAD`/`PM`：全部操作权限。
- **路由守卫：** `router.beforeEach` 拦截未登录、强制修改密码、admin 专属路由。

**可细化点：**
- `REVIEWER` 角色的「评审」专属菜单或功能未单独体现（当前菜单与 `DEVELOPER` 相同，仅操作权限更严格）。
- 需求提到「PM/Tech Lead（查看）」，当前 `PM`/`TECHLEAD` 实际拥有查看+操作权限（可合并/关闭 MR），与需求「查看」略有差异，但属于合理权限放大。

**关键文件：**
- `SecurityConfig.java`（安全配置）
- `UserController.java`（用户/角色管理）
- `LayoutView.vue:59-72`（动态菜单）
- `BoardController.java:155-177`（数据范围）
- `DashboardView.vue:384-403`（操作权限）

## 三、差异汇总与建议

| 序号 | 差异项 | 影响 | 建议 |
|---|---|---|---|
| 1 | **状态看板缺少「CI 检查中」列** | 需求 7 列，实际 6 列 | 这是 v2 有意设计（CI 作为独立维度）。若需求严格坚持 7 列，需恢复 `ci_checking` 列并调整 `BoardStatusCalculator` 优先级。 |
| 2 | **多维筛选缺少「按 Reviewer」** | 需求 5 维度，实际 4 维度 | 前端筛选栏增加 Reviewer 输入框；后端 `BoardController.getBoard` 增加 `reviewer` 参数，SQL 对 `reviewers` 字段做 `LIKE` 匹配。 |
| 3 | `REVIEWER` 角色菜单差异不显著 | 角色体验不够鲜明 | 可为 `REVIEWER` 增加「待我评审」快捷视图或独立菜单，提升角色体感。 |

## 四、核验结论

当前代码实现 **满足 10 项需求中的 8 项完全满足、2 项部分满足**。
- 核心功能（同步、看板、CI、冲突、拖拽、详情、报表、导出、权限）均已实现且质量较高。
- 主要差异集中在**状态看板列数（6 vs 7）**和**筛选维度（4 vs 5）**两处，属于产品定义层面的细微差异，不影响系统可用性。
