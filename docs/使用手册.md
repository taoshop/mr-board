# MR Board System 使用手册

> 版本：v1.0.0 | 适用分支：`master` | 最后更新：2026-07-29

---

## 一、系统简介

MR Board 是一个支持 **GitHub / GitLab 双平台** 的 Merge Request 看板系统，帮助团队实时追踪代码评审状态、CI 构建结果，并生成每日汇总报表。

### 核心功能

| 模块 | 说明 |
|------|------|
| **看板** | 拖拽式管理 MR 状态：待处理 → 冲突待解决 → 已关闭 |
| **多维筛选** | 按仓库、作者、Reviewer、标签、时间区间组合筛选 |
| **实时同步** | 每 5 分钟自动同步 Git 平台数据，支持手动触发 |
| **CI 监控** | 展示最新 Pipeline 状态及成功率趋势 |
| **统计报表** | 每日 MR 吞吐量、平均处理时长、CI 成功率 |

## 二、登录与账号管理

### 2.1 首次登录

打开系统地址（根据部署方式不同）：

- **Docker 部署**：`https://localhost`
- **本地开发**：`http://localhost:5173`

默认管理员账号：

| 字段 | 值 |
|------|-----|
| 用户名 | `admin` |
| 密码 | `Admin@123` |

> ⚠️ 生产环境请务必在「用户管理」中修改默认密码。

### 2.2 账号锁定解锁

连续 **5 次** 登录失败后，账号将被锁定 **15 分钟**。

**手动解锁（Docker 环境）**：

```bash
docker exec mr-board-redis redis-cli DEL "login:fail:<用户名>"
```

### 2.3 权限说明

| 角色 | 权限 |
|------|------|
| `admin` | 看板管理、用户管理、报表查看、系统配置 |
| `user` | 看板查看、报表查看 |

## 三、看板操作

### 3.1 看板布局

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  待处理      │  │ 冲突待解决   │  │  已合并      │  │   已关闭     │
│ (pending)   │  │ (conflict)  │  │ (merged)    │  │  (closed)   │
└─────────────┘  └─────────────┘  └─────────────┘  └─────────────┘
```

- **待处理**：新建或待 Review 的 MR
- **冲突待解决**：代码存在冲突，需开发者处理
- **已合并**：已通过 Review 并完成合并
- **已关闭**：被拒绝或手动关闭的 MR

### 3.2 多维筛选

点击看板顶部的筛选栏，支持以下维度组合筛选：

| 筛选条件 | 说明 | 示例 |
|----------|------|------|
| 仓库 | Git 仓库名称 | `mr-board` |
| 作者 | MR 提交者用户名 | `zhangsan` |
| **Reviewer** | 指定评审人（支持模糊搜索） | `lisi` |
| 标签 | MR 关联的 Git 标签 | `bugfix` |
| 时间区间 | MR 创建时间范围 | `2026-07-01` ~ `2026-07-29` |

> 💡 **Reviewer 筛选**：输入 reviewer 用户名的一部分即可实时过滤，支持中文和英文名。

### 3.3 拖拽变更状态

在看板中，你可以将 MR 卡片从一个列拖拽到另一个列，系统会自动更新其状态。

**特殊规则**：

- 拖拽到 **已关闭** 列时，系统会调用 Git 平台 API **真实关闭 MR**（支持 PATCH 方法）。
- 如果卡片显示 "人工状态"，表示该状态是手动拖拽覆盖的，不会随同步自动改变。

### 3.4 状态自动计算规则

系统根据 Git 平台数据自动判断 MR 所在列：

| Git 状态 | 看板列 |
|----------|--------|
| `open` + 无冲突 + 未通过 Review | 待处理 |
| `open` + 存在冲突 | 冲突待解决 |
| `merged` | 已合并 |
| `closed` | 已关闭 |

> 如果 Reviewer 已评论但未 Approve，仍视为 **待处理** 状态。

## 四、数据同步

### 4.1 自动同步

系统默认每 **5 分钟** 自动从 Git 平台同步一次数据：

- MR 列表及状态
- CI Pipeline / Job 结果
- Reviewer 分配信息

### 4.2 手动触发同步

点击看板右上角的 **「立即同步」** 按钮，可手动触发全量同步。

同步过程中：

1. 页面顶部会显示进度提示
2. 同步完成后，看板数据会自动刷新（WebSocket 实时推送）
3. 无需手动刷新页面

### 4.3 同步代理配置（可选）

如果 GitHub 访问受限，可在 Docker Compose 中配置代理：

```yaml
environment:
  SYNC_PROXY_ENABLED: true
  SYNC_PROXY_HOST: host.docker.internal   # Windows Docker Desktop
  SYNC_PROXY_PORT: 7897
```

## 五、统计报表

### 5.1 查看日报

进入 **「报表」** 菜单，可查看每日汇总数据：

| 指标 | 说明 |
|------|------|
| 新增 MR 数 | 当日创建的 MR 数量 |
| 已合并 MR 数 | 当日完成合并的 MR 数量 |
| 平均处理时长 | 从创建到合并的平均耗时 |
| CI 成功率 | 当日 CI 通过次数 / 总次数 |

### 5.2 报表数据为空的排查

如果报表始终显示 0 或成功率 0%：

1. 确认 CI 同步已正确获取 `started_at` 字段（查看数据库 `ci_jobs.started_at` 是否有值）
2. 若历史数据缺失，执行修复：
   ```sql
   UPDATE ci_jobs SET started_at = created_at WHERE started_at IS NULL;
   ```
3. 重新触发报表计算：调用 `POST /api/reports/admin/trigger-summary`

### 5.3 导出报表

报表页面支持导出为 Excel，点击 **「导出」** 按钮即可下载。

## 六、常见问题

### Q1：看板数据没有实时更新

**排查**：

1. 检查浏览器控制台是否有 WebSocket 连接错误
2. 确认 Nginx 配置中 `/ws/` 路径已正确代理到后端
3. 手动点击「立即同步」按钮触发刷新

### Q2：Reviewer 筛选无结果

**排查**：

1. 确认该 MR 在 Git 平台上确实分配了 Reviewer
2. 检查同步是否已完成（Reviewer 信息依赖最近一次同步）
3. 尝试只输入 Reviewer 用户名的前几个字母进行模糊匹配

### Q3：拖拽 MR 到「已关闭」报错

**现象**：拖拽后提示 "Git平台操作失败: Invalid HTTP method: PATCH"

**原因**：旧版本后端使用 JDK 内置 HTTP 客户端，不支持 PATCH 方法。

**解决**：确保后端版本已引入 `httpclient5` 并替换为 `HttpComponentsClientHttpRequestFactory`。

### Q4：报表 CI 成功率始终为 0%

**原因**：`ci_jobs.started_at` 字段为 NULL，日报统计按 `started_at` 范围过滤。

**解决**：

1. 确认 `GitHubClient` / `GitLabClient` 已映射 `startedAt`
2. 修复历史数据：`UPDATE ci_jobs SET started_at = created_at WHERE started_at IS NULL`
3. 重新触发报表计算：`POST /api/reports/admin/trigger-summary`

### Q5：前端提示 "网络错误" 无法登录

**排查步骤**：

1. 检查浏览器 DevTools → Network，确认请求是否到达 `https://localhost/api/auth/login`
2. 如果是 CORS 错误（`blocked by CORS policy`）：
   - 确认后端 `app.cors.allowed-origins` 包含 `https://localhost`
   - 检查 `docker-compose.yml` 中 `APP_CORS_ALLOWED_ORIGINS` 环境变量
3. 如果是 502 Bad Gateway：
   - 后端容器可能还在启动中，等待 10~15 秒后重试
   - 查看后端日志：`docker compose logs -f backend`
