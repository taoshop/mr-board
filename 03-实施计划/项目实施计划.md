## 2. 实施策略

### 2.1 策略概述
采用**迭代增量开发**模式，按功能优先级分 5 个阶段推进。每个阶段产出可独立运行和验收的最小可用版本，确保核心业务价值尽早交付。

### 2.2 优先级原则
1. **阻塞优先**：数据同步与看板展示是后续所有功能的基础，最先实现
2. **读优先于写**：先保证数据能正确展示，再支持交互操作
3. **内部操作优先于外部同步**：看板内部状态流转先于 Git 平台双向同步
4. **核心报表优先于高级分析**：先保证基础统计可用，再细化维度

## 3. 阶段一：基础架构与认证授权（第 1 ~ 2 周）

### 3.1 阶段目标
搭建完整的前后端运行框架与数据库环境，实现用户登录、角色权限控制、系统管理基础能力，为后续业务功能开发提供底座。

### 3.2 前置条件
- 开发环境（Node.js 20+、JDK 17+、MySQL 8.0+、Redis 7+）就绪
- Git 仓库初始化，分支模型（main / develop / feature/*）建立

### 4.5 交付物
- 可对接真实 Git 平台的看板只读版本

### 4.6 风险与应对
| 风险 | 应对措施 |
|---|---|
| Git API 限频导致同步失败 | 增加请求间隔（500ms）、失败重试 3 次、记录失败日志 |

| 看板大数据量渲染卡顿 | 前端虚拟滚动（单列 > 50 条时启用），后端分页返回 |

实现看板的核心交互能力：拖拽变更状态、CI 状态深度集成、合并冲突醒目标识、MR 详情侧边栏，提升看板的实用性与操作效率。

| 验收项 | 验收标准 | 验证方式 |

| 权限控制 | Developer 无法拖拽他人 MR；Reviewer 无拖拽权限 | 多账号权限测试 |

| CI 详情 | 详情面板正确展示 CI Stage/Job 状态，日志链接可点击跳转 | 页面操作验证 |
| Webhook 同步 | Git 平台操作（新建 MR / 合并）后 10 秒内看板自动更新 | 端到端操作验证 |
| 合并/关闭操作 | Tech Lead 拖拽 MR 到"已合并"列，Git 平台实际执行合并，系统状态同步更新 | 全流程测试 |
| 操作审计 | 所有手动状态变更可在数据库 `mr_status_history` 中查到记录 | 查库验证 |

### 5.5 交付物
- 支持交互操作的完整看板页面
- MR 详情侧边栏
- Webhook 即时同步能力
- 操作审计日志

### 5.6 风险与应对
| 风险 | 应对措施 |
|---|---|
| Git API 合并权限不足 | 合并操作前校验 Token 权限（`developer` 权限无法 merge），权限不足时仅更新本地状态并提示 |
| 拖拽频繁触发后端请求 | 前端防抖（debounce 500ms），拖拽松开后才发请求；失败时卡片动画回弹 |
| Webhook 网络不通 | Webhook 作为增量同步补充而非唯一机制，定时同步兜底 |

## 6. 阶段四：统计报表与数据导出（第 8 ~ 9 周）

实现多维统计报表（概览指标、趋势图、分布图）与 Excel/CSV 导出功能，满足 PM 与 Tech Lead 的数据分析与汇报需求。
