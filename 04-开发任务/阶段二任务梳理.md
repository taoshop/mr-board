# 阶段二任务梳理：Git 数据同步与看板只读展示

## Git 分支合并请求（MR）状态看板系统

---

## 1. 文档信息

| 项 | 内容 |
|---|---|
| 阶段名称 | 阶段二：Git 数据同步与看板只读展示 |
| 计划工期 | 第 3 ~ 5 周（15 个工作日） |
| 目标产出 | 可对接真实 Git 平台的 MR 看板只读版本（含数据同步、看板展示、基础筛选） |
| 前置条件 | 阶段一验收通过，已有可用的 GitLab/GitHub 测试项目 |
| 关联文档 | 《系统 PRD 文档》《技术方案文档》《项目实施计划》 |

---

## 2. 阶段二总体排期

```
Week 3（第 3 周）
├─ Day 1 ~ 2：数据库设计 + Git 源配置模块
├─ Day 3 ~ 4：Git API 抽象层 + GitLab 客户端实现
└─ Day 5：GitHub 客户端实现 + API 连接测试

Week 4（第 4 周）
├─ Day 6 ~ 7：MR 数据同步服务（全量/增量 + 状态映射 + CI 同步）
├─ Day 8：Quartz 定时任务 + 手动同步接口 + 同步日志
└─ Day 9 ~ 10：看板后端接口（按列分组 + 多维筛选）

Week 5（第 5 周）
├─ Day 11 ~ 12：前端看板页面（7 列布局 + 卡片组件 + 空状态）
├─ Day 13：前端筛选面板 + 看板刷新机制
├─ Day 14：前端 Git 源配置页面 + 同步日志页面
└─ Day 15：前后端联调 + 性能优化 + 阶段验收
```

## 8. 阶段二新增技术要点

### 8.1 Git API 调用策略
- **分页处理**：GitLab 默认每页 20 条，设置 `per_page=100` 减少请求次数
- **请求间隔**：连续 API 调用间休眠 200~500ms，避免触发限流
- **重试机制**：HTTP 429/5xx 时自动重试 3 次，间隔 1s、2s、4s 指数退避
- **并发控制**：单 Git 源同步时串行执行项目，避免并发请求过多

### 8.2 状态映射算法伪代码
```java
public BoardStatus calculate(MR mr) {
    if (platformStatus == MERGED) return MERGED;
    if (platformStatus == CLOSED) return CLOSED;
    if (hasConflict || !mergeable) return CONFLICT;
    if (ciStatus == RUNNING || ciStatus == PENDING) return CI_CHECKING;
    if (reviewers != null && !reviewers.isEmpty() && commentsCount > 0) return IN_REVIEW;
    if (ciStatus == SUCCESS && mergeable) return MERGEABLE;
    return PENDING_REVIEW;
}
```

### 8.3 缓存策略
- **看板数据缓存**：Redis Key = `board:{userId}:{md5(filterParams)}`，TTL = 120s
- **同步状态缓存**：Redis Key = `sync:running:{gitSourceId}`，防止同一源并发同步
- **用户权限缓存**：登录时缓存用户权限列表，TTL = 30min，减少数据库查询
